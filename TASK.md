# Triton Kernel Optimization Harness

You are an expert in CUDA and Triton kernels. Your job is to produce a high-performance Triton kernel matching a reference PyTorch implementation. Work proceeds in **three strictly-gated phases**. Do not skip, merge, or reorder them.

## Phases

| Phase | Command | Input | Output | Forbidden |
|-------|---------|-------|--------|-----------|
| 1. Learn | `/phase1-learn` | `context/`, `.claude/skills/` | `knowledge/*.md` | Writing to `solution/`, running benchmarks |
| 2. Implement | `/phase2-implement` | `input/`, `knowledge/` | Fused reference + subgraph specs + correct kernel with frozen autotune configs | Skipping the fuse/extract stages, Phase-3-style algorithmic rewrites |
| 3. Optimize | `/phase3-optimize` | Working `solution/`, `HINTS.md`, frozen autotune configs | Optimized `solution/` + `ITERATIONS.md` | Re-running autotune sweeps without an algorithmic change, rewriting from scratch |

Each phase has its own entry prompt in `.claude/commands/`. Do not read or execute another phase's prompt while in the current phase, **unless you are running under `/run-all`**, which auto-chains all three phases in one session and advances `.claude/state/current_phase` between them.

## Phase Gating

Before taking any action, verify the current phase by reading `HANDOFF.md`. If `HANDOFF.md` is missing or empty, you are in **Phase 1**. Do not start a phase whose entry conditions are not met. Do not end a phase without writing the exit artifact to `HANDOFF.md`.

**Entry conditions:**
- Phase 1: `context/` populated; `knowledge/` is empty or only contains `README.md`/`_template.md`.
- Phase 2: `knowledge/` contains at least one non-template knowledge file; `HANDOFF.md` shows Phase 1 complete.
- Phase 3: `solution/` passes `bash scripts/bench.sh` with `CORRECT=True`; `HANDOFF.md` shows Phase 2 complete.

**Exit conditions:**
- Phase 1: Knowledge base covers the kernel family (see `knowledge/README.md` for required topics). Append Phase 1 block to `HANDOFF.md`.
- Phase 2: `solution/fused_reference.py`, `solution/subgraph_specs.json`, `solution/fusion_notes.md`, `solution/rules_check.md`, and `solution/autotune_notes.md` all exist. `bash scripts/bench.sh` prints `CORRECT=True` on the autotuned baseline. Both `[baseline]` and `[baseline-autotuned]` commits exist. Append Phase 2 block to `HANDOFF.md`.
- Phase 3: Iteration budget exhausted OR user stops the run. `ITERATIONS.md` up to date. Append Phase 3 block to `HANDOFF.md`.

## Rules

- `RULES.md` applies at all times. It defines what counts as cheating (e.g., delegating compute to PyTorch APIs, no-op kernels).
- Your goal is genuine latency reduction — not a high reported speedup ratio. Do not use stream injection, process injection, timing-function patches, or any other reward hacking.
- Do not fabricate benchmark results. Every claim of speedup must be backed by a `bash scripts/bench.sh iter-N` run captured under `trajectory/`.

## Directory Layout

```
TASK.md                       # this file — orchestrator
RULES.md                      # anti-cheat invariants (shared across phases)
HINTS.md                      # profiling + optimization guidance (Phase 3)
HANDOFF.md                    # phase-to-phase state log
ITERATIONS.md                 # Phase 3 iteration history
.claude/
  commands/
    phase1-learn.md           # Phase 1 entry prompt
    phase2-implement.md       # Phase 2 entry prompt
    phase3-optimize.md        # Phase 3 entry prompt
  skills/                     # reusable capabilities (kernels/, optimization/, system/)
context/                      # reference materials (Phase 1 input)
input/                        # starting kernel + reference PyTorch (Phase 2 input)
knowledge/                    # structured knowledge base (Phase 1 output)
  README.md                   # topics required in the knowledge base
  _template.md                # entry template
solution/                     # working kernel (Phase 2 + Phase 3 output)
  fused_reference.py          # Phase 2.1 — code-to-code fused PyTorch
  fusion_notes.md             # Phase 2.1 — fusion decisions + rationale
  subgraph_specs.json         # Phase 2.2 — typed subgraph specs
  rules_check.md              # Phase 2.4 — anti-cheat self-audit
  autotune_notes.md           # Phase 2.5 — frozen winning configs per workload
  workload_classes.json       # Phase 3.A — workload classification by bottleneck
  triton/kernel.py            # Phase 2.3/2.5/3.C — production kernel
bench/                        # benchmark runner (do not modify)
scripts/
  bench.sh                    # generated by Phase 2 setup
trajectory/                   # per-iteration artifacts (auto-populated)
```

## Session Start

For a fresh end-to-end run from an empty `HANDOFF.md`, invoke `/run-all`. It auto-chains Phases 1 → 2 → 3 in a single session, advancing `.claude/state/current_phase` between phases so the `PreToolUse` write gates stay correct. To resume an existing run mid-pipeline, use the steps below to detect the current phase from `HANDOFF.md` and invoke the matching per-phase command — the per-phase commands behave exactly as before and are unaffected by `/run-all`.

On every new session:
1. Read this file, `RULES.md`, and `HANDOFF.md`.
2. Determine the current phase from `HANDOFF.md`.
3. Invoke the corresponding slash command (`/run-all` for a fresh run, otherwise `/phase1-learn`, `/phase2-implement`, or `/phase3-optimize` to resume).
4. Do nothing else until the phase prompt (or the `/run-all` orchestrator) tells you to.
